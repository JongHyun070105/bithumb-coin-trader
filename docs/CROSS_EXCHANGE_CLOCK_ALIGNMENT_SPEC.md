# 이기종 거래소 시계 정렬 및 타임스탬프 시맨틱스 사양서 (Cross-Exchange Clock Alignment Specification)

> [!IMPORTANT]
> **시계 정렬의 핵심 원칙:**
> 빗썸, 업비트, 바이낸스는 각각 서로 다른 자체 서버 시계와 NTP 오차, 그리고 서로 다른 타임스탬프 세그먼트를 가진다. 따라서 거래소 간 이벤트를 정렬하거나 레이턴시를 비교할 때 거래소 제공 시계를 직접 비교하면 **미래 정보 누수(Lookahead)** 및 **인과성 역전(Causality Inversion)**이 발생한다.

---

## 1. 사용 가능한 3대 시계 도메인

| 시계 종류 | 소스 | 특성 | 주 용도 | 금지 사항 |
| :--- | :--- | :--- | :--- | :--- |
| **Exchange Timestamp ($T_{\text{ex}}$)** | 거래소 매칭 엔진 | 거래소 자체 시계, 불연속적, 윤초/오차 가능 | 체결 이벤트 정렬 (단일 거래소 내부) | 거래소 간 직접 비교 금지 |
| **Local Wall Receive ($T_{\text{wall}}$)** | EC2 호스트 OS 시계 | Chrony/Amazon Time Sync 동기화 (UTC) | UTC 시간 단위 파티셔닝, 일자별 집계 | 엄격한 이벤트 인과관계 정렬 금지 (NTP 스텝 조정 시 역전 가능) |
| **Local Monotonic Receive ($T_{\text{mono}}$)** | POSIX `CLOCK_MONOTONIC` | 절대 역전되지 않는 단조 증가 시계 | **이벤트 도착 인과 순서 정렬, 수신 지연 측정** | 서버 재부팅 후 절대 시간 비교 금지 |

---

## 2. 태스크별 시계 적격성 매트릭스

| 분석 태스크 | 적격 시계 | 사유 및 규칙 |
| :--- | :--- | :--- |
| **단일 거래소 내부 체결 순서** | $T_{\text{ex}}$ + 시퀀스 번호 | 거래소 매칭 엔진의 체결 순서를 보존함 |
| **거래소 간 선도-지행 (Cross-Exchange Lead/Lag)** | **$T_{\text{mono}}$** | 수집기 호스트에 도달한 물리적 관측 시점을 기준으로만 신호 생성 가능 |
| **네트워크 수신 지연 (Latency)** | $T_{\text{wall}} - T_{\text{ex}}$ (추정치) | 순수 네트워크 레이턴시가 아닌 '시맨틱 지연'으로 취급 (하드웨어 탭 미사용) |
| **아카이브 파티션 및 파일명** | $T_{\text{wall}}$ (UTC) | UTC 시간 기준 코호트 분할에 사용 |

---

## 3. 거래소별 타임스탬프 주의사항

1. **Bithumb:**
   - 호가 데이터에는 체결 시각이 아닌 호가 생성 시각이 포함됨.
   - 마이크로초 단위가 아닌 밀리초 단위 정밀도 제공.
2. **Binance:**
   - WebSocket 스트림에서 이벤트 생성 시각(`E`)과 거래소 매칭 시각(`T`)이 구분됨.
   - 오더북 diff 스트림의 경우 final update ID(`u`) 기반 정렬 필수.
3. **Upbit:**
   - 틱 단위 스트림에서 `trade_timestamp`와 `timestamp`(수신 스트림 시각)가 제공됨.
